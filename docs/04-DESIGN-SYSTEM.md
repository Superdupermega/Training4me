# 04 — DESIGN SYSTEM (Material Design 3, deliberately plain)

Design goal: a gym app you can read at arm's length, operate with one sweaty
thumb, and never have to think about. Material 3 out of the box. No bespoke
components where an M3 one exists.

---

## 1. Colour — M3 tokens

Source colour: **`#1E5F4B`** (deep green — calm, not a "hustle" red).
Generate a full M3 tonal palette from it and expose the standard role tokens.

| Role | Use |
|---|---|
| `primary` / `onPrimary` | main actions: Start session, Log set |
| `primaryContainer` | today's session card |
| `secondary` | supporting chips (tempo, rest, RPE) |
| `tertiary` | accents on PR / achievement |
| `error` | missed reps, pain flag |
| `surface`, `surfaceContainerLow/High` | cards, sheets, app bars |
| `outlineVariant` | dividers |

Both **light and dark** schemes ship in v1. Dark is the default in the session
player (gyms are dark, phones are bright).

Semantic aliases layered on top (defined once in `src/theme/tokens.ts`):
```
tierMain     = primary            // T1, the big lift
tierSecondary= secondary
tierAccessory= tertiary
readinessGood/ok/low = M3 green/amber/red containers
```

## 2. Typography

Material 3 type scale, single family: **Roboto Flex** (or Roboto). Overrides:
- `displaySmall` for the current weight in the player (must read from 1 m away)
- `headlineSmall` for exercise names
- `labelLarge` for slot letters (A, B, D1)
- Set numbers use **tabular figures** (`font-variant-numeric: tabular-nums`)
  so numbers don't jitter as they change.

## 3. Shape & elevation

M3 defaults: cards `medium` (12 dp), FAB/dialogs `large` (16 dp), chips `full`.
Elevation level 0–1 only; use `surfaceContainer*` tones instead of shadows.

## 4. Components (MUI ↔ M3 mapping)

| Need | Component |
|---|---|
| Navigation | `BottomNavigation` (5 items: Today · Program · Exercises · History · Profile — `src/components/nav/destinations.tsx`), `NavigationRail` ≥ 900 px. Both are always mounted; only `display` switches by breakpoint, so there is never a hydration flash from one to the other. |
| Session card | `Card` + `CardActionArea` |
| Primary action | `Button variant="contained"`, full-width, min height **56 px** |
| Set logging | custom `SetRow` built from `TextField` + `ToggleButtonGroup` |
| Rest timer | `CircularProgress determinate` + `displaySmall` countdown |
| Readiness | three `Slider`s in a `Dialog` |
| Metadata | `Chip` (tempo `30X1`, rest `90s`, RPE `@8`) |
| Substitution | `Menu` on the exercise row → "Swap exercise" |
| Feedback | `Snackbar` (never `alert`) |
| Loading | `Skeleton` matching final layout, never a spinner on a full page |

## 5. Screens

### 5.1 Onboarding wizard (6 steps, one question per screen)
1. **How many days a week can you train?** — big 2/3/4/5/6 selector. Each option
   shows what it becomes ("3 days — full-body, one heavy lift each day").
2. **How long have you been lifting?** — beginner / intermediate / advanced.
3. **What do you have?** — equipment profile cards + toggles (bar, rack, bench, bike, bands, sled).
4. **How strong are you right now?** — for squat, hinge, press, pull: either a
   known 1RM or "weight × reps I could do comfortably". Skippable → the app
   uses week 1 to calibrate at conservative loads.
5. **How long can a session be?** — 45 / 60 / 75 min, default 60.
6. **Block length** — 4 weeks (default) or 6 weeks. Then **Build my plan**.

Progress indicator on top, Back always available, answers persisted per step so
a refresh doesn't lose them.

### 5.2 `/today`
The landing destination — replaced the old `/plan` hero (chunk 15;
`/plan` now 308-redirects here).
- **Today card**, in `primaryContainer`: title, ≈ duration, the main lift and
  its top set ("Back Squat 4×5 @ 92.5 kg"), big **Start** button.
- **Next block card** underneath, so the next scheduled session is never more
  than a glance away even on a rest day.
- A week strip (4 or 6 columns, whatever the active block's length is) for
  jumping between weeks without leaving the page.
- Deload weeks are visually marked ("Deload — take it easy, that's the point").

### 5.2a `/program`
The block overview — every week, every session, and the two ways to get a
program: **Build a plan for me** (the six-question generator wizard,
`/onboarding?edit=1`) or **Build my own program** (`/program/builder`,
below). A program generated by the wizard can be duplicated into an
editable routine (`DuplicateAsRoutineButton`) without losing what's already
scheduled.

### 5.2b `/program/builder`, `/program/builder/[id]` — the routine builder
The "add and build my program myself" screen (chunk 18). A routine is a
reusable template of days → blocks → exercises, kept separate from a
scheduled program instance (`docs/02-DATA-MODEL.md` §1).
- Day tabs across the top; each day is a list of blocks (single exercises or
  supersets), reorderable with up/down icon buttons — not drag-and-drop, so
  the whole flow stays keyboard-operable without a separate keyboard path to
  maintain.
- Tapping an exercise row opens `ItemEditorSheet`: sets/reps/tempo/rest,
  target kind (`%TM` / RPE / fixed weight / bodyweight / duration /
  distance), and — the original ask — either **last time** for that exact
  exercise or the **TM-derived expected load**, whichever the target kind
  makes relevant (`ExerciseContextPanel`, chunk 19).
- Adding an exercise opens `ExercisePickerDialog` — the same browsable,
  filterable list as `/exercises`, with the same last-time/expected-load
  context line per row, in a sheet rather than a full page.
- A live, non-blocking time-budget estimate (`estimateSession`) and advisory
  warnings (`advise.ts`) — balance and volume hints, never a hard block. The
  athlete's plan is the athlete's plan.
- **Schedule this program** materializes the routine into real `t4m_session`
  rows (`materializeRoutine.ts`) that play in the exact same session player
  as a generated program — the player has no idea which one produced them.

### 5.3 `/session/[id]` — the session player (the most important screen)
- **Readiness dialog** on first open (3 sliders + Skip).
- Header: elapsed time, session title, "≈ 52 min planned", overflow menu.
- **Block accordion**: only the current block expanded. Each block shows its
  letter, name and estimated minutes.
- **Exercise card**: slot letter, name, tempo chip, cue line, "Swap" menu.
- **Set rows**: `3 × 5 @ 92.5 kg`. Tapping a row opens an inline editor with
  ±2.5 kg steppers, a rep stepper, and an RPE `ToggleButtonGroup` (6–10).
  Tick to complete. Completed rows collapse to one line with a check.
- **Rest timer** auto-starts on completion: a bottom sheet with a big countdown,
  −15 s / +15 s / Skip. Vibrate on zero if supported.
- Bottom bar: "Next block" / "Finish session".
- Wake lock on while the player is open.
- Offline chip when the outbox is non-empty.

### 5.3a `/exercises`, `/exercises/[id]` — the exercise library (chunk 16/17)
The "extensive exercise list for each muscle group" ask, ~300 movements
including a Marcus Filly / functional-bodybuilding tag
(`styles: ['functional_bodybuilding']`, 63 of them).
- `/exercises`: filterable by muscle group and style, a favourites star per
  row (`t4m_profile.favourite_exercises`). Growing the library never
  reshapes a generated program — new entries default `inGeneratorPool:
  false` and stay invisible to the generator until explicitly opted in
  (`docs/06-REDESIGN-PLAN.md` §6).
- `/exercises/[id]`: cue, tier, equipment, alternatives, contraindications,
  and the same `ExerciseContextPanel` the builder uses — last time you did
  it, or the TM-derived expected load if you never have.

### 5.4 `/history`
- **Personal records**, newest first: exercise, kind (est. 1RM / best triple
  / best five / best set), date, value.
- **Sessions**, reverse-chronological: title, weekday + date, duration,
  a readiness chip or a "Skipped" chip.
- The per-lift trend view (pick an exercise → e1RM line chart) lives on
  `/profile`'s Strength tab now, not here (see 5.5) — one home for "how am I
  trending," not two.

### 5.5 `/profile` — log & data analysis (chunk 20)
The "super advanced but user-friendly" analysis home the original ask named
as optionally living in the profile page. Four tabs, each answering one
question, hand-rolled SVG charts (no charting dependency — a personal
training log is a few hundred points at most) with an accessible `<table>`
fallback behind every chart and a designed empty state at 0/1/2 points:
- **Strength** — pick a lift (chip row) → e1RM line chart, PRs marked
  larger and gold, current training max shown alongside.
- **Volume** — weekly sets + tonnage (bar chart, gaps filled not dropped),
  and a horizontal ranking of sets by muscle group.
- **Consistency** — completed/skipped % for the active block, plus a
  12-week calendar heatmap of training days.
- **Records** — every training max and PR, filterable by muscle group (the
  same data `/history` shows, given a proper filtered home).

### 5.5a `/profile/settings`
Days per week, session cap, equipment, units, block length, "Regenerate
program" (with a clear warning that unlogged future sessions are
replaced), export data as JSON.

## 6. Interaction rules

- Tap targets ≥ 48 dp everywhere; the log-set tick is ≥ 56 dp.
- No horizontal scrolling anywhere, ever.
- Every destructive action confirms in a `Dialog` naming exactly what is lost.
- Motion: M3 standard easing, 200–300 ms. `prefers-reduced-motion` respected.
- Empty states always say what to do next, never just "No data".
- All copy is plain and calm. Coaching cues, not hype. No exclamation marks
  except the readiness green light.

## 7. Accessibility (non-negotiable)

- Contrast ≥ 4.5:1 for text, ≥ 3:1 for UI edges — verified on both schemes.
- Every icon button has an `aria-label`.
- The player is fully keyboard-operable; focus visible; focus moves to the rest
  timer when it opens and returns to the next set when it closes.
- Set completion announces via `aria-live="polite"` (`SessionPlayer.tsx`).
  The rest timer's visible countdown is deliberately `aria-live="off"` —
  announcing every tick would drown out everything else — but a separate
  hidden region announces once, the moment rest ends (`RestTimer.tsx`).
- Never encode meaning in colour alone: readiness shows a dot **and** a word.
- No nested interactive elements (a button inside a `role="button"` row
  breaks screen-reader and keyboard navigation) — every row with both a
  primary tap target and a secondary action uses true sibling controls
  (`ButtonBase` + a separate `IconButton`), not one wrapping the other.
