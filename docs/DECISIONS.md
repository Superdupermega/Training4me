# DECISIONS

Anything that contradicts or extends the specs goes here, with a date and a
reason. If code and docs disagree, this file is where the disagreement gets
resolved — and then the spec gets updated.

| Date | Decision | Why | Docs updated |
|---|---|---|---|
| 2026-08-23 | Next.js + MUI + Supabase, no ORM, no state library | Fewest moving parts for a single-user app; MUI gives Material 3 without hand-rolling components; Supabase gives auth + Postgres + RLS in one. | `00-CONTEXT.md §3` |
| 2026-08-23 | All program logic lives in pure `src/core` | The generator is the product; it must be testable in milliseconds without a database. | `03-ARCHITECTURE.md §1` |
| 2026-08-23 | Balance rules B1–B10 are hard constraints, not heuristics | "Look good, move well" only survives contact with a generator if it is enforced by validation. | `01-METHODOLOGY.md §4.4` |
| 2026-08-23 | Time budget trims accessories, never the main lift | The main part stays big as hell by construction. | `01-METHODOLOGY.md §1.3, §6.3` |
| 2026-08-24 | Balance ratios are validated on week one, not every week | Later weeks re-materialise from week one, so the movements are identical; only the wave changes set counts. Checking ratios weekly made the peak week (which has a top set and deliberately less accessory volume) fail a structural rule it cannot control. Weeks 2+ are checked on invariants instead: one main lift per session, a weekly carry, 48-hour spacing, under the cap. | `01-METHODOLOGY.md §4.4` |
| 2026-08-24 | Trim ladder drops secondary sets before the finisher | The plan had the finisher going first. Carries and trunk work are a stated Magnus principle; a third set of dumbbell press is not. | `01-METHODOLOGY.md §1.3` |
| 2026-08-24 | Accessory rounds drop from 3 to 2 on the peak week | The heaviest week has the longest main lift, so something had to give. Cutting accessory volume as intensity climbs is also just correct block periodization. | `01-METHODOLOGY.md §5.1` |
| 2026-08-24 | Movement choice prefers loadable, standard movements | The generator was picking bodyweight split squats and band lat pulldowns for someone with a full gym. Candidates are now narrowed: regressions (assisted pull-ups, band versions of cable work) only appear when nothing standard fits, and loadable movements win when there is something to load. | `01-METHODOLOGY.md §4.5` |
| 2026-08-24 | Single athlete, no auth; PIN gate instead | One user, so per-row ownership is meaningless. The t4m_ tables have RLS on with zero policies (public keys can read nothing) and all access is server-side with the service role. A missing APP_PIN in production refuses to serve rather than exposing a public log. | `02-DATA-MODEL.md §2` |
| 2026-08-25 | Chunk 14: kept `dynamic = 'force-dynamic'` on every route rather than removing it | Removing it would let Next attempt static prerendering of `/plan`, `/history`, `/settings` etc. at build time, which requires reaching Supabase from the build environment. That is not reliably available (this sandbox's network allowlist blocks it outright), so the safer win was taken instead: every repo read is wrapped in `unstable_cache` with tags (`profile`/`program`/`sessions`/`logs`), and every mutation in `actions.ts` calls `revalidateTag` for what it touched. This caches the *data fetches* regardless of the route's dynamic/static status, which is most of the available win without the build-time risk. Revisit removing `force-dynamic` in a later chunk once it can be verified against a real deploy. | `06-REDESIGN-PLAN.md` chunk 14 |
| 2026-08-25 | Chunk 14: `db()` returns a memoised singleton Supabase client | It was building a new client (URL parse, header setup) on every single call with no per-request state to justify it — `persistSession: false`, no cookies threaded through. One client for the life of the server instance. | `06-REDESIGN-PLAN.md` chunk 14 |
