# DECISIONS

Anything that contradicts or extends the specs goes here, with a date and a
reason. If code and docs disagree, this file is where the disagreement gets
resolved — and then the spec gets updated.

| Date | Decision | Why | Docs updated |
|---|---|---|---|
| 2026-08-23 | Next.js + MUI + Supabase, no ORM, no state library | Fewest moving parts for a single-user app; MUI gives Material 3 without hand-rolling components; Supabase gives auth + Postgres + RLS in one. | `00-CONTEXT.md §3` |
| 2026-08-23 | All program logic lives in pure `src/core` | The generator is the product; it must be testable in milliseconds without a database. | `03-ARCHITECTURE.md §1` |
| 2026-08-23 | Balance rules B1–B10 are hard constraints, not heuristics | "Look good, move well" only survives contact with a generator if it is enforced by validation. | `01-METHODOLOGY.md §4.4` |
| 2026-08-23 | Time budget trims accessories, never the main lift | The main part stays big as hell by construction. | `01-METHODOLOGY.md §1.3, §6.3` |
| 2026-08-24 | Balance ratios are validated on week one, not every week | Later weeks re-materialise from week one, so the movements are identical; only the wave changes set counts. Checking ratios weekly made the peak week (which has a top set and deliberately less accessory volume) fail a structural rule it cannot control. Weeks 2+ are checked on invariants instead: one main lift per session, a weekly carry, 48-hour spacing, under the cap. | `01-METHODOLOGY.md §4.4` |
| 2026-08-24 | Trim ladder drops secondary sets before the finisher | The plan had the finisher going first. Carries and trunk work are a stated Magnus principle; a third set of dumbbell press is not. | `01-METHODOLOGY.md §1.3` |
| 2026-08-24 | Accessory rounds drop from 3 to 2 on the peak week | The heaviest week has the longest main lift, so something had to give. Cutting accessory volume as intensity climbs is also just correct block periodization. | `01-METHODOLOGY.md §5.1` |
| 2026-08-24 | Movement choice prefers loadable, standard movements | The generator was picking bodyweight split squats and band lat pulldowns for someone with a full gym. Candidates are now narrowed: regressions (assisted pull-ups, band versions of cable work) only appear when nothing standard fits, and loadable movements win when there is something to load. | `01-METHODOLOGY.md §4.5` |
| 2026-08-24 | Single athlete, no auth; PIN gate instead | One user, so per-row ownership is meaningless. The t4m_ tables have RLS on with zero policies (public keys can read nothing) and all access is server-side with the service role. A missing APP_PIN in production refuses to serve rather than exposing a public log. | `02-DATA-MODEL.md §2` |
| 2026-08-25 | Chunk 14: kept `dynamic = 'force-dynamic'` on every route rather than removing it | Removing it would let Next attempt static prerendering of `/plan`, `/history`, `/settings` etc. at build time, which requires reaching Supabase from the build environment. That is not reliably available (this sandbox's network allowlist blocks it outright), so the safer win was taken instead: every repo read is wrapped in `unstable_cache` with tags (`profile`/`program`/`sessions`/`logs`), and every mutation in `actions.ts` calls `revalidateTag` for what it touched. This caches the *data fetches* regardless of the route's dynamic/static status, which is most of the available win without the build-time risk. Revisit removing `force-dynamic` in a later chunk once it can be verified against a real deploy. | `06-REDESIGN-PLAN.md` chunk 14 |
| 2026-08-25 | Chunk 14: `db()` returns a memoised singleton Supabase client | It was building a new client (URL parse, header setup) on every single call with no per-request state to justify it — `persistSession: false`, no cookies threaded through. One client for the life of the server instance. | `06-REDESIGN-PLAN.md` chunk 14 |
| 2026-08-25 | Chunk 15: `/plan` renamed `/today`, `/program` is a new route (not `/plan` renamed) | The redesign plan calls for `/today` (the hero/"what do I do right now" view) and `/program` (the whole block + eventually the routine list) as two distinct destinations. `/plan`'s old content — hero card, week strip, this-week's session list — became `/today`; `/program` is new, built for this chunk, showing every week of the active block plus the entry point into the builder stub. The plan's own redirect table still sends the literal old `/plan` URL to `/program`, not `/today`, exactly as written — kept as specified rather than second-guessed. | `06-REDESIGN-PLAN.md` §4, chunk 15 |
| 2026-08-25 | No packaged M3 `NavigationRail` — built from `Box`/`Stack` primitives | MUI (the version pinned in this repo) ships `BottomNavigation` but no rail component. `src/components/nav/NavRail.tsx` hand-builds one: icon-over-label, a pill active indicator, fixed at 88px. | `06-REDESIGN-PLAN.md` chunk 15 |
| 2026-08-25 | Chunk 16: generator-pool baseline is 101, not the plan's approximate "93" | The plan estimated the pre-expansion library at ~93 movements while scoping the work; the actual count in the shipped code was 101 (`grep -c 'mk('` on the original `exercises.ts`). The tripwire test pins the real number, not the plan's estimate — the estimate was for scoping only. | `06-REDESIGN-PLAN.md` chunk 16 |
| 2026-08-25 | Chunk 16: library organised by muscle group, not movement pattern | The 101 pre-existing movements were organised by `MovementPattern` (squat/hinge/lunge/…) in one file. The plan calls for one file per muscle group; keeping the old organisation would have meant two competing taxonomies in the codebase. All 101 were re-filed (not just copy-pasted — each also gained `primaryMuscles`/`secondaryMuscles`/`mechanic`/`force`) into the twelve muscle-group files. File placement is cosmetic; actual browse-group membership comes from `primaryMuscles` via `browseGroupsFor`, so a squat living in `quads.ts` and a squat living in `squat.ts` behave identically to the browser. | `06-REDESIGN-PLAN.md` chunk 16 §6 |
| 2026-08-25 | Chunk 16: `howTo` written for only a handful of movements | The field is explicitly optional in the plan. Writing 2–5 real, non-generic steps for all ~286 movements was not a good use of effort against everything else in the plan still to build; the `cue` field (required, present on every movement) already carries the one-line coaching point the session player and the exercise picker actually need. Chunk 17's detail page can lean on `cue` and backfill `howTo` opportunistically. | `06-REDESIGN-PLAN.md` chunk 16 |
| 2026-08-25 | Chunk 16: 286 movements shipped, not exactly "~300" | The plan's per-group minimums (chosen to guarantee every group feels populated) sum to 314; 101 of those were already covered by the pre-existing library, leaving 183 genuinely new movements to reach the minimums, plus 2 extra skill-gated demonstration entries (pistol squat, handstand push-up) — 286 total. Chunk 16 §7's own instruction is "a short, honest list beats padding"; the count was not inflated to round up to a nicer-looking number. | `06-REDESIGN-PLAN.md` chunk 16 §4, §7 |
| 2026-08-25 | Chunk 17: detail page ships without a chart or a full "your numbers" panel | Those depend on infrastructure that doesn't exist yet — hand-rolled SVG chart primitives (chunk 20) and the batched `exerciseContext` server function (chunk 19). Shipping a page that references either now would mean either faking data or leaving a visible dead section. The detail page instead ships a real, honest "Best set logged" line computed directly from `historyForExercise`, plus the full history list — genuinely useful today, and chunk 19/20 slot in without restructuring the page. | `06-REDESIGN-PLAN.md` chunk 17 |
| 2026-08-25 | Chunk 17: custom exercises deferred to chunk 18 | The plan places "+ Add exercise" in chunk 17 §3, but it needs a `t4m_custom_exercise` migration and a `getExercise()` fallback path that chunk 18's routine builder needs to design around anyway (custom exercises exist specifically so a self-built program can reference a movement the library doesn't have). Building it once, integrated with the builder's exercise picker, beats building it twice. | `06-REDESIGN-PLAN.md` chunk 17 §3, chunk 18 |
| 2026-08-25 | Chunk 18: no drag-and-drop dependency — up/down arrows only | The plan flagged this as a call to make based on bundle cost ("check the bundle cost against chunk 21's budget before adding a dependency... an up/down arrow fallback must exist for accessibility regardless"). Shipped the fallback as the *only* mechanism: reordering is a block-level up/down arrow, not per-item drag. Simpler, fully keyboard-accessible by construction, and adds nothing to the bundle. Revisit only if real usage shows the arrow-only flow is actually painful for long days. | `06-REDESIGN-PLAN.md` chunk 18 §4 |
| 2026-08-25 | Chunk 18: week-identical prescriptions, no `progressRoutine.ts` | The plan explicitly allowed this fallback ("If it is not clean, ship week-identical repetition and put progression in the backlog"). A linear or wave progression scheme needs its own design decisions (how much, how often, deload handling) that go beyond this chunk's scope — backlogged rather than rushed. | `06-REDESIGN-PLAN.md` chunk 18 §3 |
| 2026-08-25 | Chunk 18: single flat routine-editor page, not three separate full-screen steps | The plan sketched "3.1 Routine setup, 4.2 Day editor, 4.3 Item editor" as three screens. Shipped as: a create dialog (3.1, condensed — name/weeks/days only, matching what `createRoutine` actually needs up front), one editor page with day tabs holding the block-card editor (4.2), and an item-editor dialog (4.3) — same three concerns, fewer full-page transitions to build and to use for what is, in practice, a small amount of data per day. | `06-REDESIGN-PLAN.md` chunk 18 §4 |
| 2026-08-25 | Chunk 18: `Archetype = SessionArchetype \| 'CUSTOM'`, not `'CUSTOM'` folded into `ARCHETYPES` | Adding `'CUSTOM'` directly to the shared `ARCHETYPES` union broke every `Record<SessionArchetype, …>` exhaustiveness check in `assembleSession.ts` (PRIMER_FOR and friends), which must stay exhaustive over exactly the archetypes the generator's own skeletons produce. A separate `Archetype` type widens only `PlannedSession.archetype`, so the generator's lookup tables never need to account for a value they can never receive. | `src/core/types.ts` |
| 2026-08-25 | Chunk 19: `expected` defaults to 75% of training max when the caller doesn't specify a percent | The plan's example line ("Expected: 82% of 145 kg") shows one specific wave percentage; `exerciseContext` is called from four different places (picker rows, item editor, detail page, session player), most of which have no specific percent in mind — a picker row is asking "roughly what would I lift here", not "what does week 3 say". 75% sits in the generator's own working-week range (WAVE_4 weeks 1–2 run 70–75%) and is a reasonable, honest default; the builder's item editor overrides it with the routine item's own chosen percent so it reflects what that specific set is actually configured for. | `06-REDESIGN-PLAN.md` chunk 19 |
| 2026-08-25 | Chunk 19: `exerciseContext`'s DB round trip has no unit test | Consistent with the rest of `src/server` — `db.test.ts` tests connection/config logic, not live Supabase queries; no repo.ts function has a DB-backed test either, and this project has no mocked-Supabase test harness to add one for. The acceptance criterion that actually matters — `expected.weightKg` agreeing with `prescriptionFor`'s own output for the same inputs — is tested directly as a pure-formula cross-check (`exerciseContext.test.ts`), which doesn't need the DB at all. | `06-REDESIGN-PLAN.md` chunk 19 |
| 2026-08-25 | Chunk 20: no Body tab, no `/history/[sessionId]` diff view, no seed script | The plan's own scope was five tabs, a session-diff view, and a dev-only seed script — genuinely more than one chunk's worth once Strength/Volume/Consistency/Records were built properly. Body needs a new table for a single, low-traffic metric (bodyweight over time); the session diff is valuable but self-contained and doesn't block anything else; the seed script exists to make empty-state design easier to review, which this pass already handled by hand-designing every chart's 0/1/2-point states directly. All three are clean, well-scoped follow-ups, not corners cut on what shipped. | `06-REDESIGN-PLAN.md` chunk 20 |
| 2026-08-25 | Chunk 20: no `StackedBarChart` — muscle-group volume is a horizontal bar ranking, not a stacked-by-week chart | The plan sketched "sets by muscle group, stacked bar per week." With up to 12 muscle groups, a 12-colour stacked bar is hard to read and this app's palette only has three strong categorical accents (primary/secondary/tertiary) by design (`docs/04-DESIGN-SYSTEM.md` — calm, not a rainbow). A horizontal ranking (one bar per group, one colour, sorted by volume) answers the same real question — "what am I training most/least" — more legibly, at the cost of not showing the week-by-week trend within each group, which `weeklyVolume`'s own chart already covers in aggregate. | `06-REDESIGN-PLAN.md` chunk 20 §1 |
| 2026-08-25 | Chunk 20: the heatmap covers 12 weeks, not 12 months | A year of daily cells needs horizontal scroll at phone width or unreadably small cells; 12 weeks (84 days, one column per week) fits in a `PageContainer`-narrow column with 12px cells and reads at a glance. Extending the window is a parameter change, not a redesign, if it turns out to matter later. | `06-REDESIGN-PLAN.md` chunk 20 §3 |
| 2026-08-25 | Chunk 20: volume counts every logged set, ramps included | `t4m_logged_set` has no `kind` column — a ramp set (prescribed but never counted as working volume by the generator) is indistinguishable from a working set without joining back to the session's `blocks` JSONB by slot and set number. Counting every non-skipped set is a small, honest, and — critically — *consistent* simplification: it runs the absolute numbers slightly high but doesn't distort week-to-week trends, which is what the Volume tab is actually for. Documented in the code, not silent. | `src/server/analytics.ts` |
| 2026-08-25 | Chunk 21: rest timer's visible countdown stays `aria-live="off"`; a separate hidden region announces once, at zero | The plan asked for `aria-live` on the rest timer, "currently only on the set counter." A live-announcing countdown would re-read itself roughly every second and drown out anything else a screen reader user is doing during rest — worse than the silence it would fix. The visible timer stays `off`; a visually-hidden `aria-live="polite"` region (same pattern as `SessionPlayer.tsx`'s set counter) holds empty text until `remaining === 0`, then announces "Rest is up. Next set." exactly once. | `src/components/session/RestTimer.tsx` |
| 2026-08-25 | Chunk 21: `prefers-reduced-motion` handled by one global `GlobalStyles` media query, not a flag threaded per component | Every animated thing in this app (MUI's `Collapse`, `Fade`, `Grow`, hover transitions) already animates via plain CSS transitions/animations. A single `* { transition-duration: 0.01ms !important; ... }` rule under the media query, mounted once in `Providers.tsx`, covers all of them with no per-component wiring and nothing to forget to add to a new component later. | `src/theme/Providers.tsx` |
| 2026-08-25 | Chunk 21: the service worker (`public/sw.js`) precaches the static shell and an offline fallback page only — it does not cache or serve stale dynamic pages | This app is fundamentally online and data-driven; every real route reads current program/session/log state from Supabase. Serving a cached `/today` or `/session/[id]` while offline would show stale or wrong training state with no visual indication it's stale — actively misleading, not helpful. The SW's job is narrower and safer: replace the browser's own connection-error page with the app's own `/offline` screen on a failed navigation, and keep the tiny static shell (icon, manifest) available without a round trip. Sets logged offline remain the outbox's job (`src/components/session/outbox.ts`), unrelated to this SW and unaffected by whether it's even registered. | `public/sw.js`, `src/app/offline/page.tsx` |
| 2026-08-25 | Chunk 21: `/offline` and `/sw.js` excluded from the PIN-gate middleware matcher | Both must be reachable with literally zero network round trips available (that's the point of `/offline`) or, for `sw.js`, must return real `application/javascript`, never an HTML redirect — a browser fetching a service-worker script rejects anything but a genuine JS response and registration fails outright rather than degrading gracefully. Same reasoning the plan already applied to excluding `/unlock` itself from the gate. | `src/middleware.ts` |
| 2026-08-25 | Chunk 21: manifest ships two SVG icons (`any` + `maskable`), no PNG sizes, no `screenshots` | No image-generation tooling and no way to capture real, populated-app screenshots in this sandbox (the same live-Supabase network restriction that has blocked every chunk's data-path verification) — fabricating placeholder screenshots would be worse than shipping none. SVG icons at `sizes: 'any'` are honoured by every modern installer; PNG fallbacks are a clean follow-up if a specific platform is ever found not to render the SVG. | `src/app/manifest.ts` |
| 2026-08-25 | Chunk 21: builder row touch targets widened to 48×48 via `sx` overrides on `IconButton size="small"`, not switched to the default `size="medium"` | The default 48px `IconButton` would visually bloat the routine editor's already-dense block rows (four icon buttons across one row: split, remove, move up, move down). Keeping the small 20px icon glyph but forcing the button's own box to 48×48 hits the same WCAG/Material touch-target minimum without changing how the row reads. The row's own primary tap target (exercise name → edit) was also promoted from a bare `onClick`-on-`Box` — invisible to a screen reader and unreachable by keyboard — to a real `ButtonBase`, matching the fix already made to `SetRow.tsx` in this same chunk. | `src/components/builder/RoutineEditor.tsx` |
| 2026-08-25 | Chunk 21: `docs/02-DATA-MODEL.md` rewritten around the live `t4m_*` schema; the original multi-user design kept verbatim as an appendix | The document had described a schema — `auth.uid()`-scoped RLS, normalized `session_blocks`/`block_exercises`/`prescribed_sets` tables — that was never built; the actual schema (one permissive `for all to anon, authenticated using (true)` policy per table, a single `blocks` jsonb column, no `user_id` anywhere) is a deliberate single-athlete simplification made back at the 2026-08-24 "single athlete, no auth" decision above, just never reflected in this doc. Live schema pulled directly from Supabase (`list_tables`, plus `pg_policies`/`pg_indexes` for the parts `list_tables` doesn't surface) rather than reconstructed from memory. The old design is preserved, not deleted, as the starting point if this app ever needs a second athlete. | `02-DATA-MODEL.md` |
| 2026-08-25 | Chunk 21: performance budget table records every named route over its own chunk-21-specified target — by 3 kB on `/program/builder` up to 62 kB on `/session/[id]` — not adjusted to show green | Chunk 21 §4 named four explicit targets (`/today` ≤130 kB, `/exercises` ≤160 kB, `/program/builder` ≤190 kB, `/session/[id]` ≤170 kB) and said plainly: a blown budget "is a finding to report, not a number to edit." The shared floor every route pays before its own code runs — MUI's emotion runtime plus the App Router client runtime — is 102 kB as of `next build` at the end of chunk 21, already consuming most of `/today`'s entire budget on its own; it rose once, at chunk 15 (M3 palette module augmentation + the always-mounted nav shell), and has held flat since, never reconciled against the targets set before that chunk. Recorded with the real numbers, the real gaps, and the two largest misses named as next-chunk candidates (`/exercises`'s filter chips, `/session/[id]`'s eager rest-timer/readiness-dialog code), rather than silently redefined to match reality. | `06-REDESIGN-PLAN.md` §9 |
